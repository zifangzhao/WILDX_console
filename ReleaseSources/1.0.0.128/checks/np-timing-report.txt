Remaining physical limits / Yoshi's question
The common PC coordinate and first-source-row mapping are implemented and tested.
A simultaneous compatible NP+GPIO recording is still missing. Such a joint run
without an independent physical input can establish shared epoch/units, event
coverage and transport consistency, but cannot identify unknown constant probe
ADC/filter/serialization/receiver or GPIO edge/IRQ delays. Those unobservable
terms prevent a defensible approximately1ms physical AP-to-GPIO bound. GPIO's
integer-ms RTC phase and query interval also remain in its own event bounds.
The new 67–135us NP clock intervals do not remove those terms. No external wiring
was added. Historical RM032 files cannot gain missing acquisition anchors.

IMU remains separate from NP row timing. The old V2 capture's1399 snapshots all
have enabled1/valid0/sequence0/imu_tick0/sensor_time0/chipID0, IMU error1 and
IO-errors2. That is no valid AG sample observed, not a host transport-loss proof.
The new V2 run again reports1399 snapshots and0 distinct valid IMU samples.
V1's new run has14017 distinct observations,0 sequence gaps/queue overflow and
802 estimated missed conversions; latest-register polling is not lossless FIFO.
Firmware-owner source review confirms imu_tick_ms is the I2C-completion IRQ's
HALms; sensor_time_24 is a free-running counter latched at register-read start,
not ADC conversion time. V2 publishes latest snapshots at at most20Hz, so those
records cannot reconstruct every200Hz sample. A separate future IMU native-row
sidecar can retain existing sequence/counter/IRQms/session/validity and coarse
PC bounds. Full-rate capture needs firmware queue/batch transport; tighter sensor
read-clock mapping needs burst-start/end counter brackets and reset binding.
Neither the held1250Hz analogin grid nor NP timing alone supplies missing samples
or physical IMU filter/update phase. This assessment does not implement that
separate IMU acquisition work or claim historical recovery of absent data.
